# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A browser-based CAM tool (Angular 22, standalone components, zoneless change detection). The user defines 2D **shapes** and cutting **tools/operations** in a form-driven editor; the app converts shapes into polygons, routes toolpaths, and emits G-code, while previewing both shapes and toolpaths in a Three.js viewport. There is no backend — everything runs client-side and deploys to Firebase Hosting.

## Commands

- `npm start` / `ng serve` — dev server at http://localhost:4200 (development config, no optimization).
- `npm run build` / `ng build` — production build to `dist/`.
- `npm test` / `ng test` — Karma + Jasmine unit tests in headless/Chrome. Run a single spec by temporarily narrowing with `fdescribe`/`fit`, or `ng test --include='**/some.spec.ts'`. Headless: `ng test --watch=false --browsers=ChromeHeadless`. Specs sit next to what they test (`src/cam/*.spec.ts`, `src/worker/**/*.spec.ts`); the test build can't bundle clipper2-wasm, so specs only import modules that don't (Clipper-based work lives in separate files, e.g. `clipper-transforms.ts`, `regions.ts`). The test config has no Zone.js polyfills (the app is zoneless).
- Formatting via Prettier (`.prettierrc`); HTML uses the `angular` parser.

Deployment is automated by GitHub Actions (`.github/workflows/firebase-hosting-*.yml`): PRs get preview channels, merges to the default branch deploy live.

## Architecture

The whole app is a set of RxJS observable pipelines. There is no NgRx/state-management library — the reactive graph *is* the state. Where things live:

- `src/app/services/` — `ModelStore` (the `model$` source of truth, loading a `.nc` file; persistence in `model-persistence.ts` over the app database in `app-db.ts`), `CamService` (wires model → shapes → G-code → toolpaths, plus preview highlight/hidden shapes, the stock view, the time estimate, the job checks, the simulation and the downloads: G-code, one file per tool, cut list, setup sheet), `ModelHistory` (undo / redo, see below), `WorkTracker` (`working$` / `isWorking$`).
- `src/app/pipeline/` — framework-free pipeline functions: `shapes.ts` (`generateShapesFromModel`, transform chaining), `shape-svg.ts` (`createSvgFromShape`), `gcode.ts` (`generateGcodeFromOperations`), `operation-inputs.ts` (resolves an operation against its tool/overrides and the operation it borrows from), `route-operation.ts` (the per-type worker call), `vcarve-source.ts` (what clearings, inlay plugs and rest machining borrow), `point-pattern.ts` (the `points` shape, made on the main thread), `geometry-settings.ts`, `preview.ts`, and shared operators (`shareLatest`, `distinctJson`, `distinctItems`) in `operators.ts`.
- `src/app/app.component.ts` is layout only: the toolbar across the top (`toolbar/`, presentational: the project's name, status and menu on the left, New / Templates / Load .nc / G-code on the right; labels drop out as the window narrows), the editor and the preview below, split by `editor-divider/` (resizable, width persisted). What the toolbar does to the project, with its dialogs, is `ProjectCommands` (`projects/project-commands.service.ts`); the preview refits on `ModelStore.replaced$`. File download / `.nc` parsing helpers are in `src/app/project-file.ts`.
- `templates/` (repository root) — example projects for the toolbar's Templates menu: `.nc` files with the project embedded (a downloaded G-code file works), copied to the build as assets under `templates/` (`angular.json`, build and test). `scripts/templates-index.mjs` lists them in `templates/index.json` (gitignored; written by the `prestart` / `prebuild` / `pretest` npm hooks, or `npm run templates` — plain `ng serve` / `ng test` skip it); a template's name is its file name unless the file has a `; name: …` line, and `; description: …` adds one. The menu fetches the list (`listTemplates`, `src/app/templates/index.ts`); opening a template replaces the project (`ModelStore.openTemplate`); templates must hold a project in the current format — there's no conversion of older ones. `templates.spec.ts` checks every listed template's ids and references.
- `src/app/projects/` — projects the user saves by name in this browser (the toolbar's Projects menu and Save button): app database stores `projects` (id, name, time — listed without loading models) and `projectModels` (the model by id). `ModelStore` keeps which saved project the open work belongs to (persisted with the open project as `projectId`, so it survives a reload) and its model as saved; `pending$` compares the work with it by `sameWork()` (`model-editor/same-work.ts`), which ignores what only the editor changes — `expanded`, undefined properties, and a field's Formly `defaultValue` where the other model lacks the field (projects saved before a field existed) — after resolving stock / G-code options (the editor clears hidden ones); so a freshly opened project isn't "changed". Work that isn't a saved project is pending when it isn't empty. Opening a template, a `.nc` file or starting a new project detaches the work from its project; replacing work asks first only when something is pending.
- **Undo / redo** (`services/model-history.service.ts`, toolbar buttons, Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y outside text fields): snapshots of the work from `changes$`; edits within a second join one step; what only the editor changes isn't a step (`sameWork` on the store's normalised `work()`, ignoring properties the newer state lacks — the editor drops hidden fields). `ModelStore.restore()` puts a state back without `replaced$`; replacing the work clears the history.

### The data flow

```
model$ (ModelType)  ──►  shapes$ (CamShape[])  ──►  program$ (Program)  ──►  paths$
   ▲                          │                          │
 form edits                 (viewer)                download / model metadata
```

1. **`model$`** is the single source of truth: a `BehaviorSubject<ModelType>` persisted to IndexedDB (database `cnc-utils`, store `project`; debounced, and on `pagehide`). It's read before the app starts (`provideAppInitializer(preloadModel)`); when IndexedDB can't be used it falls back to localStorage (key `model`), and the newer copy is loaded. IndexedDB because imported files (SVG, traced images as data URLs) outgrow localStorage. Pipelines consume `ModelStore.changes$`, which drops value-equal models (compared by `deepEqual` against a snapshot that copies objects but shares strings, so big embedded files cost nothing per keystroke) and is shared — don't add side effects to it per subscriber. `ModelType = { variables, shapes, tools, operations, stock, gcode }`; each operation references a tool (`toolId`) and a shape (`shapeId`). Models are loaded as stored (storage, saved projects, `.nc` metadata, templates): projects in older formats aren't supported, so a change to the model's format doesn't need a migration. `emptyModel()` (`model-editor/model.ts`) is a new project.
2. **`generateShapesFromModel`** turns each shape into a `CamShape[]` observable. Each shape is rasterized to an SVG string (`createSvgFromShape`) and sent to the worker's `importSvg`, *except* `boolean` shapes, which combine a list of other shapes' outputs in order (`operands`: the first is the starting point, each later one has its own operation; `applyBooleanOperations` in the worker), `copy` shapes, `text` shapes, which go to the worker's `importText` (Google Fonts fetched from Fontsource/jsDelivr at a pinned version, parsed with opentype.js; URLs in `src/cam/font-source.ts`), `trace` shapes, which go to the worker's `traceBitmap` (marching squares in `src/cam/marching-squares.ts`), and `points` shapes, made on the main thread (single-point polygons — `{ points: [p], close: false }` — mean drill points; the viewer draws them as crosses). Operations get their shape with `ShapeResults.byId(id)`, so other shapes changing doesn't wake them. Transforms are then chained: each transform's output feeds the next transform's input; a transform toggled off (`disabled`) passes its input through unchanged.
   `nest` shapes lay out copies of other shapes on a sheet (`src/cam/sheet-nesting.ts`: MaxRects on their bounding boxes, a gap apart, inside a margin, turned 90° only where an item allows; parts that don't fit go on further sheets, `nestSheet` picks the one shown); `nest-layer` shapes place other shapes (dados, grooves) wherever a nest's part goes, by the part's box (`pipeline/nest.ts`). `hinge-cup` (the cup and screw holes of a European hinge, door edge on the X axis) is made on the main thread like `points`; `bowtie` is an SVG outline. A shape marked `clamp` is a keep-out zone: drawn red, cuts coming within a bit's radius are flagged (not a routing input — `ShapeParameters` omits it).
   **Tabs** belong to shapes, not operations: the `tabs` transform (`transform-tabs.ts`, `placeTabs` in `src/cam/tabs.ts`) adds `CamShape.tabs` — convex footprints (a rectangle across the line, outside / inside / both ways, evenly spaced from each loop's first point, or one on the line nearest each of a list of points — `tabPlacement: 'points'`, `tabPoints` a point list, see below) with a `top` Z. Transforms carry them: affine ones (`applyMatrixTransform`, `transformShapes` — so repeat, polar, mirror copy them) move them with the shape, the others keep them where they were (`keepingTabs` in `apply-transform.ts`); booleans keep their operands' tabs and `copy` shapes copy them. So a tabs transform before a repeat gives every copy the same tabs.
3. **`generateGcodeFromOperations`** walks `operations` in order, resolves the referenced tool by `toolId` and shape by `shapeId`, runs the operation (`routePocketHole` / `flatOutline` / `routeProfile` / `routeVCarve` / `routeVCarveClearing` / `routeDrill` / `routeHelix` / `routeChamfer` / `routeRest`) in the worker, keeps every operation's moves out of the tabs on all the shapes operations cut (`keepTabs` in `src/cam/tabs.ts`, run in the worker after routing, so changing tabs doesn't re-route: the tool goes up to a tab's top where its centre comes within its radius of the footprint, and back down after), and emits a `Program` (the operations' `GCodeBuilder`s + G-code options, including the stock's `offset`); `buildProgram` writes it out. The stock offset (G-code zero on the stock — or, with the G-code `referencePoint` option, a point of the cuts' bounding box moved to a given X/Y: `programOffset` in `src/cam/stock.ts`) is applied only to the written G-code; the preview and `programTime` (the time estimate) work in design coordinates. The preview never writes G-code: `programPaths` walks the program into `CamPath[]`, and `reuseUnchangedPaths` (`pipeline/preview.ts`) keeps unchanged paths' identity so the viewer only redraws what changed. The G-code menu can also split the program into one file per tool run (`buildProgramPerTool`, zipped by `src/app/zip.ts`), write the cut list (`cut-list.ts`: nests' placements, else the outlines outside profiles cut) and open a printable setup sheet (`setup-sheet.ts`). Only on download is the current model gzip+base64 encoded (`src/app/store.ts`) and embedded as a `; model=` comment so a `.nc` file can be re-loaded to restore the project. So edits that don't change toolpaths (renames, hiding) don't rebuild the G-code.

A key pattern in both `generate*` functions: a `scan` operator keeps a per-id list of long-lived inner pipelines. On each model emission, existing entries are **mutated in place** (push new params into their `BehaviorSubject`s) rather than rebuilt, so heavy worker computations only re-run when their specific inputs actually change. New ids create new pipelines; this is intentional incremental memoization — preserve it when editing.

`working$` is a zero-emission observable that increments/decrements a work-lock counter on subscribe/unsubscribe; it's `race`d against worker calls to drive the `isWorking$` spinner. Cancelling (unsubscribing) a worker call drops its result; the worker gets `CANCEL_GRACE` to finish (so it's reused, with clipper and fonts already loaded) and is terminated only if it runs over.

### Web worker layer (`src/worker/`)

CPU-heavy geometry runs off the main thread. The boundary is **type-safe via a Proxy contract**:

- `src/worker/work/` exports plain functions (e.g. `importSvg`, `applyTransform`, `routePocketHole`, `flatOutline`, `routeProfile`, `applyBooleanOperation`), each returning an `Observable`. Add a new work function by exporting it and re-exporting from `src/worker/work/index.ts` — nothing else needs registration.
- `src/worker/index.ts` exposes `worker` as a `Proxy` typed as `Contract` (derived from the work functions). Calling `worker.someWork(args)` returns an Observable that, when subscribed, queues a job for a pool of workers (`MAX_WORKERS`: CPU count − 1, capped; idle workers are kept 5 minutes). The first value (or completion, or error) comes back as a `JobOutcome`.
- `src/worker/codec.ts` packs what crosses the boundary: `CamShape`s (exactly `{ sourceShapeId, polygons }`, optionally `tabs`) and `GCodeBuilder`s become typed arrays (results are transferred, not copied). Anything else passes as is.
- `src/worker/main.worker.ts` is the worker entry: it looks up the function by name in `work` and runs it. In production builds results that took over `MIN_CACHED_MS` are kept in IndexedDB (`result-cache.ts`, database `cnc-utils-results`), keyed by a 128-bit hash of the job's name and packed arguments plus the worker's own URL (which changes with its code), so a reload doesn't recompute everything. Work functions must therefore be pure functions of their arguments. Worker code is compiled with `tsconfig.worker.json`.
- Geometry uses **clipper2-wasm** (`src/cam/clipper.ts`) for boolean ops and path offsetting/inflation. The `.wasm` asset is wired into the build in `angular.json`.

### Model editor (form-driven, `src/app/model-editor/`)

The editor UI is **entirely generated from ngx-formly field configs** — there are no hand-written shape/tool forms. The model type and the form schema are co-defined:

- `shapes/`, `transforms/`, `operations/`, `tools/` each have an `index.ts` that aggregates its members into both a discriminated-union `ModelType` and a Formly `field` config.
- Each individual shape/transform/operation file (e.g. `shape-circle.ts`, `transform-rotate.ts`, `operation-flat.ts`) exports a `ModelType` interface (with a `type` discriminator) and a `Definition` (`{ type, label, fieldGroup }`). The field group uses `expressions.hide` keyed on `model.type` so only the selected variant's fields show.
- **To add a new shape/transform/operation:** create the file with its `ModelType` + `Definition`, then register it in the relevant `index.ts` (add to the union and the `[...]` array). For shapes, also add a case to `createSvgFromShape` in `pipeline/shape-svg.ts` (unless it's handled like `boolean`); for operations, add a case to the `switch (op.type)` in `pipeline/route-operation.ts` and, typically, a matching work function in `src/worker/work/` (see `operation-profile.ts` + `route-profile.ts` for a recent end-to-end example). Operations can depend on other operations: `v-carve-clear` borrows its shape, V-bit and depths from the referenced v-carve (`vCarveSource()` in `pipeline/vcarve-source.ts`), so it regenerates whenever that v-carve changes. Depth is normally capped at the V-bit's cone height (`vCarveGeometry`); when a clearing for the v-carve comes earlier in the list (`clearedFirst` in `pipeline/vcarve-source.ts`), both go to the full max depth (`beyondCone`) — the shank then only moves through cleared space; shared V-groove geometry lives in `src/cam/vcarve-geometry.ts`.
- Profiles can take a finishing pass (after `leaveStock`, once all paths are cut, on the line at full depth), an onion skin (the passes stop that much above full depth; a last pass cuts through it once every path is cut) and arc lead-ins / lead-outs on the waste side (`withLeads`, `src/cam/leads.ts`: the loop becomes an open path cut the same way round every pass). `keyhole` (a keyhole bit: plunge at each point, run the slot, come back) and `flat-plug` (a flat-bottomed inlay's plug: the outline a pocket's end mill really clears — `reachable` — less a glue gap, optionally mirrored, cut with an outside profile; it borrows the pocket like rest machining, `flatPlugSource`) are operations too.
- Operations that cut in steps down (pocket, profile, flat — and rest, through its pocket) share their depth fields: `depthStepsFields()` in `operations/depth-steps.ts` (start depth, `depthMode` — `depth` read per step or as the total — and `steps`; switching the mode converts `depth` so the cut stays the same). Read them through `depthPerStep()` / `totalDepth()`, never `op.depth` directly.
- Operations that borrow from another operation: `v-carve-clear` (a `v-carve` or an `inlay-plug`), `inlay-plug` (the female `v-carve`; carves round the mirrored design, reaching start depth × tan(V/2) into it at the surface — `worker/work/inlay-plug.ts`; each level is the area round the design offset by that less its inset, never an inset of the grown area, which would round the plug's corners), and `rest` (a `pocket`, and that pocket's tool). `borrowedShapeId()` (`operations/describe.ts`) finds the shape they cut. Which bits an operation accepts is `allowedBits` in `operations/index.ts` (bit types: end mill, ball nose, bull nose, v-bit, drill).
- Each tool has an `index`, its `T<n>` in the G-code (`toolNumber()` in `tools/index.ts`), so reordering the list doesn't renumber tools; it must be unique (validated on the field), a new tool gets the lowest free one, and the tools list shows it in each tool's badge instead of its position (`props.itemPrefix` on `repeat`), and tool pickers / operation descriptions before the tool's name (`numberedToolLabel()`). It's not a routing input (`ToolParameters` omits it).
- The tools list has a **Library** button (`props.headerActions` on the `repeat` type) opening `ToolLibraryDialogComponent`; library tools are kept in the app database (store `tools`) for every project, and export/import as JSON (`tools/tool-library.ts`).
- Typed lists of points — a tabs transform's `tabPoints`, a `points` shape's `pointsList`, a `polyline`'s `polylinePoints` — are `pointListField()` (`model-editor/point-list.ts`): an inline `repeat` of `{ id, x, y }`, each coordinate a number field, so an expression; the pipelines take them through `finitePoints()` (`src/cam/point-patterns.ts`), which leaves out points that can't be worked out.
- A `path-data` shape is a list of SVG path commands, `pathCommands` (`shapes/shape-pathdata.ts`): an inline `repeat` of `{ id, command, …parameters }`, the command letter (upper case absolute, lower case relative) choosing which number fields (each an expression) and arc flags show (`parametersOf()`); `pathCommandsData()` (`src/cam/path-commands.ts`) writes them out for `createSvgFromShape`, stopping at a number that can't be worked out. The list's **Import** button (`PathDataDialogComponent`, a `headerActions` entry that `replace`s the list) reads pasted path data with `parsePathData()` (the full SVG grammar: implicit repeats, numbers and arc flags run together), reporting where it fails.
- Custom Formly types (`repeat`, `file` — text, or a data URL with `props.readAs: 'dataUrl'`, `hidden`) and the `group` wrapper (a boxed, optionally collapsible keyless field group) live in `model-editor/components/` and are registered in `src/app/app.config.ts`, along with a `whole-number` validator.
- **Variables and expressions** (`variables/`): the `variables` list (first section, edited inline — `props.inline` on `repeat`) holds named values; each may be an expression using the ones above it (`evaluateVariables`, evaluated in order). Every `type: 'number'` field accepts an expression too: the `number` type is replaced by `NumberTypeComponent` (registered after the Bootstrap types in `app.config.ts`), which stores a plain number as a number and anything else as the typed string. The parser is hand-written (`variables/expression.ts`, no `eval`); a number literal can carry a length unit (`UNITS`: `1cm` is 10, mm when there's none; a fraction of whole numbers takes it as a whole, `1/4in`). The field suggests variables (only those above, for a variable's own value — `fieldScope`), constants, functions and, after a number, units (`variables/suggest.ts`; popup in a CDK overlay, Ctrl+Space for all), and colours the expression's parts (`variables/highlight.ts`): a coloured copy lies over the input, whose own text is transparent, kept scrolled with it; hovering any token shows what its part works out to (`sqrt(a) = 3.46` for the function name or its brackets, `a * 2 = 24` for the `*`; or why it can't be worked out) and shades that part — `explainExpression`, from the parse tree (`parse` builds it, `evaluate` works it out); the hovered token is found by the coloured pieces' positions. All that is `ExpressionEditorComponent` (`components/expression-editor.component.ts`), one line in the form or a growing, wrapping text area; the field's expand button (on hover / focus) or Alt+Enter opens the text area in `ExpressionDialogComponent`, which takes line breaks (whitespace to the parser; the one-line box shows them as spaces), shows the value as it's typed (`fieldVariables()` — a variable's own value only sees the ones above) and applies on Apply / Ctrl+Enter. The code font is Roboto Mono (Google Fonts, linked in `src/index.html`); it and the token colours are CSS variables (`--code-*`) in `styles.scss`. Because the stored model can hold strings in number fields, `CamService` feeds the pipelines `resolveModel(model, ModelFieldConfig)`, which finds the number fields by walking the Formly config (`numberSchema`) and substitutes their values (`null` when they can't be worked out); the per-item memoization then re-runs only what a variable change actually affects. The saved / downloaded project keeps the expressions. Form code that reads a number from the raw model (hide expressions, labels) must go through `numberIn(field, value)` / `resolvedModelOf(field)` (`variables/field.ts`). `numberExpressionExtension` moves number fields' `min`/`max` props to `numberMin`/`numberMax` and checks them against the evaluated value (Angular's own validators would read `"2 * a"` as 2).
- Feeds & speeds (feed rate, plunge rate, ramp, ramp angle, spindle speed) are set per tool and can be overridden per operation (`tools/feeds-and-speeds.ts`). `operationInputs` (`pipeline/operation-inputs.ts`) strips the overrides from the operation parameters and merges them into the tool (`withOverrides`): ramp settings feed routing, while feeds and spindle speed only tag the G-code, so changing them doesn't re-route.

`src/app/model-editor/model.ts` derives the parameter types (`ShapeParameters`, `OperationParameters`, etc.) by `Omit`ing the bookkeeping fields (`id`, `expanded`, `name`, `transforms`, …) via the `OmitUnion` helper in `src/util.ts`.

### CAM / G-code (`src/cam/`)

- `types.ts` — the shared geometry vocabulary: `CamPoint`, `CamPolygon`, `CamShape` (polygons + `sourceShapeId`), `CamPath`.
- `gcode-builder.ts` — fluent `GCodeBuilder` that records abstract instructions (travel/carve/plunge/feedrate/…) and renders them to G-code text with `.build()`, or straight to preview `CamPath[]` with `.toPaths()` (same walk, no text written or parsed), or into a time estimate with `.estimateTime()`. Only `.build()` fits arcs: runs of cuts along a circle, level or with a steadily changing Z (helices, ramps), become G2/G3 (`arc-fit.ts`; option `arcs`), with the centre moved onto the rounded ends' bisector so controllers accept it. Drilling can be written as canned cycles (`drillCycle`, closed with G80). Builders are immutably `clone`d and `concat`ed (`concatAll` for many). `addModelMetadata` embeds the project; `goToSafeHeight().stopProgram()` finalizes.
- `clipper.ts` — thin async wrappers over clipper2-wasm, lazily initialized via `lazy()` (region helpers on top of it in `worker/work/regions.ts`).
- `travel-order.ts` — the order an operation cuts its shapes in (`travelOrder`: nearest first, then 2-opt and Or-opt, with constraints such as holes before the outline around them — `insideFirst`), so the rapids between cuts are short. Routers use it unless the G-code option `optimizeTravel` is off (then shapes are cut as they come); it reaches them as a routing input, so toggling it re-routes.
- Pure geometry (testable without Clipper): `corners.ts` (corner analysis, fillets/chamfers, circles), `box-joints.ts`, `point-patterns.ts`, `marching-squares.ts`, `stock.ts` (stock settings and the G-code offset, `programOffset`).

### Job checks and simulation

- `checkJob` (`src/cam/job-checks.ts`, fed by `pipeline/job-checks.ts` as `CamService.warnings$`) flags, per operation: cuts more than 0.5 mm into the spoilboard, cuts deeper than the tool's `fluteLength`, steps deeper than the bit is wide, heavy engagement, corners a round bit leaves rounded on the parts cut out (no dogbone / corners transform), parts cut free with no tabs or onion skin, and toolpaths within reach of a clamp. The viewer lists them; the setup sheet prints them.
- The simulation (`src/cam/simulate.ts`, the worker's `simulateStock`) sweeps each operation's bit profile along its cuts over a heightmap of the stock (or a block round the cuts), about 400k cells; `CamService.simulation$` only runs while the viewer's Simulate toggle is on (enabled operations only), and again only when the paths, their bits or the stock change. The viewer draws it as a closed solid (`viewer/helpers/stock-solid.ts`: the surface, the bottom and walls, holes where it's cut through) standing on the grid.

### Viewer (`src/app/viewer/viewer.component.ts`)

Three.js renderer that draws `CamShape[]` (shape outlines, one line object per shape; tabs as cyan blocks from their top down to the stock's bottom, or the deepest cut) and `CamPath[]` (toolpaths, travel vs. carve colored differently; paths of the same operation, move type and shape are drawn as one `LineSegments`, with direction arrows per path), the stock box and the G-code's zero, with a grid helper. It also lists the job checks, draws clamps red, measures between two clicks (snapping to shape vertices; M, Esc) and shows the simulated material as a lit solid in place of the toolpaths (S). Pure presentation — it consumes the observables from `CamService`.

## Conventions & gotchas

- **Zoneless change detection** is enabled (`provideZonelessChangeDetection`). Don't rely on Zone.js auto-detection; UI updates flow through the `async` pipe on observables. Components use `ChangeDetectionStrategy.Eager` (added by the Angular 22 migration to keep pre-22 behaviour).
- Node 24.15+ (or 26+) is required (Angular 22): `.nvmrc` pins 24 for local work (`nvm use`); CI builds with Node 26.
- The worker parses SVG with `@xmldom/xmldom`, which lacks `querySelectorAll`; `svg-import.ts` adds a tag-name-only version that three's `SVGLoader` needs.
- IDs are generated with `generateId()` (random base64url) in `src/util.ts`; equality of params is checked with `deepEqual` / `JSON.stringify` in `distinctUntilChanged` to avoid redundant worker work.
- When touching the reactive graph in `src/app/pipeline/`, respect the `scan`-based memoization (mutate existing entries, create only for new ids) or you'll cause every operation to recompute on every keystroke.
- The worker contract is structural: a function exported from `src/worker/work/` is automatically callable as `worker.<name>()` with full types. Keep signatures serializable (structured-clone-able).
